How MoScribe works

Local speech-to-text with speaker separation and on-device summaries. Nothing leaves this machine.

The pipeline

  1. 1 Capture

    The browser records 24 kHz mono audio and cuts a window at the quietest point near the boundary, so words are not sliced mid-syllable.

  2. 2 Voices

    WeSpeaker ResNet34 turns each utterance into a 256-dimension voiceprint; clustering groups them into speakers. Uploads are cut at speaker turns, so a label is right by construction.

  3. 3 Recognition

    VibeASR.cpp — VibeVoice-ASR-BitNet, 1.58 GB, I8_S encoder and I2_S language model — transcribes each window on the CPU, faster than real time.

  4. 4 Stitching

    Overlapping windows are merged with a sliding matcher that tolerates transcription drift at the seams, so a sentence is never printed twice.

  5. 5 Thinking

    BitNet b1.58 2B-4T, served by llama.cpp, writes summaries, minutes and action items. It reads only your transcript and runs on the same machine.

Using it

Live

Press the orb or Space. Speak normally; text lands roughly every ten seconds. Press again to finish — the last window is transcribed before the session closes.

Upload

Drop a wav, mp3, m4a, flac, ogg or mp4. Windows are planned at speaker turns and transcribed in order; the progress bar counts them.

Speakers

Each voice gets a colour and a name. Click a name to rename it — the change carries into copy and export. Names the app hears in an introduction ("my name is Anna") are offered as a suggestion, never applied silently.

Prompts

Context biases recognition toward names and jargon. Pick a preset (meeting, clinical, legal, Amtsdeutsch…) or write your own, then apply it. The active prompt is shown as a tag.

AI actions

Summarize, Minutes, Action items, Clean up, translate, or ask your own question. Results stream in the side panel and can be copied, downloaded as .txt/.md/.json, mailed, or shared.

Models

Settings → Model picks any GGUF in models/llm/ and exposes threads, context, temperature, output length and repeat penalty. Applying reloads the model and reports the load time.

Who built it

Development

Designed and built by Mohammed at kmail.at, working with Hermes Agent as the engineering assistant. The app is a kmail product; the interface, diarisation work and local-model integration were shaped over this build.

Built on

  • VibeASR.cpp — VibeVoice-ASR-BitNet (MIT)
  • WeSpeaker ResNet34-LM — speaker embeddings
  • BitNet b1.58 2B-4T via llama.cpp — summaries
  • FastAPI, vanilla JavaScript, no build step

How it was developed

  • Local-first from the start: every model runs on this Mac, no API keys, no upload.
  • Speaker labels replaced an MFCC heuristic once measured voiceprints proved far more reliable.
  • Uploads are cut at diarised speaker turns, which is what makes labels stable.
  • The transcript renders incrementally, so streaming text never flickers.
  • German generation was tested and deliberately left off: at 2.4 B the model invents facts when forced to write German.

Privacy

Audio, transcripts and summaries stay on disk under this app's folder. History is local JSON; deleting a session removes its files.
